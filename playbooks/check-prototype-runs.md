# Skill: 프로토타입 실행 검증

## 목적
프로토타입을 **실제 브라우저에서 띄워** 동작을 확인한다.
Critic이 코드를 읽기 전에 가장 먼저 실행한다.

> 코드만 읽으면 "렌더링해봐야 아는 문제"를 놓친다.
> JS 에러로 화면이 백지여도, 소스만 보면 요구사항을 모두 충족한 것처럼 보인다.
> 종료 조건의 "주요 Interaction을 **직접 확인**할 수 있다"는 이 Playbook으로 충족된다.

## 사용하는 Agent
- Critic Agent (주 사용, 첫 번째로 실행)

## 전제
- `prototype/index.html`이 존재한다.
- `specs/user-flow.md`에 Happy Path가 정의되어 있다.

---

## 절차

### 1. 로컬 서버 기동
`file://`로 열면 일부 브라우저에서 스크립트와 `sessionStorage`가 차단된다. 반드시 HTTP로 띄운다.

```bash
cd prototype && python3 -m http.server 8000
```

검증이 끝나면 서버를 종료한다.

### 2. 브라우저로 열기
`/browse` 스킬로 `http://localhost:8000`에 접속한다.

### 3. 콘솔 에러 수집
페이지 로드 직후 콘솔을 확인한다. **에러가 1건이라도 있으면 Critical 후보다.**

| 유형 | 심각도 | 예 |
|------|--------|-----|
| JS 문법/참조 에러 | **Critical** | `Uncaught ReferenceError`, `SyntaxError` |
| 리소스 404 | **Critical** | `styles.css`, `app.js` 로드 실패 |
| 런타임 에러 | Major | 클릭 시 `undefined` 접근 |
| 경고 | Minor | deprecated API |

### 3-1. 상태 제어 쿼리로 시작점 고정
프로토타입은 `playbooks/build-prototype-html.md`의 **상태 제어 규약**을 따른다.
검증 시나리오마다 해당 쿼리로 진입해 시작 상태를 명시적으로 만든다.

| 쿼리 | 용도 |
|------|------|
| `?reset=1` | 저장된 상태를 비우고 기본 시드로 복원 — **모든 시나리오의 시작점** |
| `?seed=0` | 데이터가 전혀 없는 신규 사용자 — Empty State 검증 |
| `?state=loading` | Loading State 강제 표시 |
| `?state=error` | Error State 강제 표시 |

이 쿼리가 동작하지 않으면 프로토타입이 규약을 구현하지 않은 것이다. **Major로 기록한다.**
상태를 띄울 방법이 없으면 상태 검증 자체가 불가능하다.

### 4. 화면별 스크린샷 (375px / 1440px)
`specs/screens.md`의 모든 화면을 두 뷰포트에서 캡처한다.

각 스크린샷에서 확인할 것:
- 화면이 **비어 있지 않은가** (로드 실패 시 백지)
- 레이아웃이 깨지지 않았는가 (요소 겹침, 영역 이탈)
- 375px에서 **가로 스크롤**이 발생하지 않는가
- Primary CTA가 **하나만** 보이는가 (Mobile/Desktop 중복 렌더링이 흔한 실수)
- 텍스트가 잘리거나 넘치지 않는가

### 5. Happy Path 완주
`specs/user-flow.md`의 Happy Path를 **클릭으로 끝까지 수행한다.**

각 단계에서:
- 다음 화면으로 이동하는가
- 클릭했는데 아무 반응이 없는 요소가 있는가
- 뒤로 가기가 동작하는가
- 뒤로 갔을 때 이전 선택·필터가 유지되는가 (`manage-state` 검증)

**막다른 화면(Dead End)** — 되돌아갈 수단이 없는 화면이 있으면 Critical이다.

### 6. 상태 전환 확인
Default 외의 상태를 **실제로 띄워본다.** 마크업만 있고 전환되지 않는 경우가 많다.

| 상태 | 띄우는 방법 |
|------|------------|
| Empty | 결과가 0건이 되는 필터 조합을 입력 |
| Loading | 비동기 동작 트리거 (목업 지연이 있으면 그 사이 캡처) |
| Error | 의도적으로 실패하는 입력, 또는 해당 트리거 |

전환되지 않는 상태는 **"마크업만 존재"**로 리포트에 기록한다.

## 검증
- 로컬 서버로 띄웠는가? (`file://` 아님)
- 콘솔 에러를 수집했는가?
- 모든 화면을 375px과 1440px에서 캡처했는가?
- Happy Path를 **클릭으로** 끝까지 수행했는가?
- Default 외 상태를 실제로 띄워봤는가?
- **보고한 버그가 도구 오탐이 아님을 확인했는가?** (위 "도구 오탐 먼저 배제하기")
- 서버를 종료했는가?

## 도구 오탐 먼저 배제하기

**이 Playbook에서 가장 흔한 실패는 앱 버그가 아니라 검증 도구의 오탐이다.**
"버그를 찾았다"고 리포트하기 전에 아래를 먼저 확인한다.
오탐을 Critical로 올리면 멀쩡한 코드를 고치게 되고, Refine 횟수만 소모한다.

### 1. 화면에 여러 상태가 동시에 보인다

텍스트 추출 명령은 보통 `textContent`를 읽으므로 **`hidden` 속성이나 `display:none`으로 숨긴 요소까지 함께 반환한다.**
Empty·Error·Loading·Default를 미리 마크업해두는 이 하네스의 구조에서는 전부 한꺼번에 나온다.

> ❌ "Empty State와 Default가 동시에 렌더링됨 — 상태 머신 버그"

**확인 방법** — 실제 가시성을 직접 묻는다:
```js
[...document.querySelectorAll('#<screen> .state')]
  .map(e => ({ state: e.dataset.state, visible: e.offsetParent !== null }))
```
`offsetParent !== null`인 것이 하나뿐이면 정상이다. 스크린샷으로도 확인할 수 있다.

### 2. 클릭했는데 아무 반응이 없다

클릭 명령의 **출력을 버리지 않는다.** `2>/dev/null`이나 `>/dev/null 2>&1`로 가리면
도구가 낸 에러가 앱의 무반응과 구분되지 않는다.

흔한 원인:
| 증상 | 원인 |
|------|------|
| `Selector matched multiple elements` | 선택자가 여러 개에 매칭. 더 구체적으로 지정하거나 snapshot의 @ref를 쓴다 |
| 클릭은 됐는데 변화 없음 | 뷰포트에서 **숨겨진 쪽**을 집었다. 같은 `href`가 PC 헤더와 모바일 탭바에 중복인 경우가 흔하다 |
| 에러 없이 조용히 실패 | 다른 요소가 클릭 지점을 덮고 있다 |

**확인 방법** — 도구를 거치지 않고 페이지 안에서 직접 호출해 본다:
```js
document.querySelector('<sel>').click()
```
이걸로 동작하면 **앱은 정상이고 도구 호출이 문제다.** 선택자를 고쳐서 다시 시도한다.
이걸로도 동작하지 않으면 그때가 진짜 앱 버그다.

### 3. 비동기 지연 중에 관찰했다

정답/오답 피드백처럼 N초 뒤 다음 단계로 넘어가는 인터랙션은,
확인 명령이 그 타이머 **이후에** 실행되면 이미 초기화된 상태가 보인다.
"피드백이 표시되지 않음"으로 단정하기 전에 지연 시간을 확인하고, 필요하면 즉시 관찰한다.

### 4. 상태가 이전 세션에서 남아 있다

`sessionStorage`에 직전 검증의 상태가 남아 기대한 화면이 안 나올 수 있다.
각 검증 시나리오는 **초기화 쿼리로 시작한다** (`?reset=1` — `playbooks/build-prototype-html.md`의 상태 제어 규약).

## 실행할 수 없는 경우
브라우저 도구를 사용할 수 없는 환경(Codex 등)에서는 이 Playbook을 생략하고,
**리포트에 "실행 검증 미수행"을 명시한다.** 판정은 코드 검토 기준으로만 내리되,
`Pass` 판정에 "실행 미검증" 단서를 붙인다. 검증하지 않은 것을 검증한 것처럼 기록하지 않는다.
